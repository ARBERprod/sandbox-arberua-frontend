# Контракт фронтенду: промокоди (1С-інтеграція)

**Дата:** 2026-05-13
**Базовий план:** [2026-04-30-promocode-1c-integration-plan.md](./2026-04-30-promocode-1c-integration-plan.md)
**Результати розвідки 1С:** [2026-04-30-1c-promo-investigation.md](./2026-04-30-1c-promo-investigation.md)
**API base:** `http://localhost:8088/api/v2` (prod URL — окремо)
**Статус:** v3 (2026-05-13) — виправлено префікс маршрутів `/cart/` → `/cart-se/` (відповідно до існуючої групи в `CoreRouteRegistrar`). Решта правок з v2: §5.5 (bonus mutex), §6 edge case.

---

## 1. Передумови

- Промокод **тільки для авторизованого користувача** (Sanctum-токен у `Authorization: Bearer …`).
- У користувача має бути заповнений `phone` у профілі. Інакше apply падає з `PROMOCODE_USER_PHONE_MISSING` — UX підказка має вести в редагування профілю.
- Сертифікати/фіксовані суми не підтримуються — **тільки %-знижка**.
- 1С — джерело правди. Бек кешує лише знімок результату в `cart.promocode_data`.

---

## 2. Endpoints

### 2.1 Apply

```
POST /api/v2/cart-se/apply-promocode
Authorization: Bearer <token>
Content-Type: application/json

{ "code": "SALE15" }
```

Правила: `code` — `required|string|max:64`. Кошик мусить мати ≥ 1 позицію.

**200 OK:**
```json
{
  "success": true,
  "data": {
    "promocode": {
      "code": "SALE15",
      "discount": 15,
      "period_from": "2026-04-09T00:00:00",
      "period_to": "2026-04-11T00:00:00",
      "applied_at": "2026-05-13T10:22:31+03:00"
    },
    "cart": { /* стандартний CartResource — див. §4 */ }
  }
}
```

### 2.2 Remove

```
DELETE /api/v2/cart-se/remove-promocode
Authorization: Bearer <token>
```

**200 OK:**
```json
{ "success": true, "data": { "cart": { /* CartResource без promocode */ } } }
```

### 2.3 Deprecated alias

```
POST /api/v2/cart-se/aply-promocode   ← друкарська помилка, БУДЕ ВИДАЛЕНО
```

Той самий контракт, що `/apply-promocode`. Бек логує `legacy aply-promocode endpoint hit`. **Фронт повинен мігрувати на `/apply-promocode` до видалення.** Дата видалення — окремий PR після підтвердження міграції.

## 3. Error format

Всі помилки повертаються в єдиній формі:

```json
{
  "success": false,
  "error": {
    "code": "PROMOCODE_EXPIRED",
    "message": "Термін дії промокоду минув"
  }
}
```

`message` — локалізований текст (поточна локаль користувача, uk/ru). Фронт **не парсить `message`** — рішення приймає за `code`.

### HTTP коди

| HTTP | Коли |
|------|------|
| 401  | немає / прострочений Sanctum-токен |
| 422  | бізнес-помилки промокоду + валідація request (порожній код, max:64, порожній кошик) |
| 503  | 1С недоступний (timeout, 5xx, network) |

### Code dictionary

Фіксується остаточно до Етапу 4. Поточний список:

| Code | HTTP | Origin | UX-підказка |
|------|------|--------|-------------|
| `PROMOCODE_CODE_REQUIRED` | 422 | request validation | "Введіть промокод" |
| `PROMOCODE_CART_EMPTY` | 422 | request validation | "Додайте товари до кошика" |
| `PROMOCODE_USER_PHONE_MISSING` | 422 | local | "Заповніть телефон у профілі" + CTA → /profile |
| `PROMOCODE_NOT_FOUND` | 422 | 1С `Промокод <X> не найден!` | "Промокод не знайдено" |
| `PROMOCODE_NOT_FOR_WEB` | 422 | 1С `Промокод не действует на сайте!` | "Промокод недійсний для онлайн-замовлень" |
| `PROMOCODE_ALREADY_USED` | 422 | 1С `Клиент уже использовал промокод!` АБО race на checkout | "Ви вже використовували цей промокод" |
| `PROMOCODE_CLIENT_NOT_FOUND` | 422 | 1С `Клиент не найден!` | "Профіль не знайдено в системі лояльності" |
| `PROMOCODE_EXPIRED` | 422 | local перевірка `period_to` | "Термін дії промокоду минув" |
| `PROMOCODE_NO_ELIGIBLE_ITEMS` | 422 | local | "Промокод не діє на товари у кошику" |
| `PROMOCODE_SERVICE_UNAVAILABLE` | 503 | 1С down | "Сервіс промокодів тимчасово недоступний, спробуйте за хвилину" |

## 4. CartResource: нові поля

При наявності активного промокоду:

```json
{
  "id": "…",
  "items_count": 2,
  "total": 8500,                // фінальна сума в копійках (вже з промокодом і бонусами)
  "promocode": {
    "code": "SALE15",
    "discount": 15,
    "period_to": "2026-04-11T00:00:00",
    "total_discount": 1500       // сумарна знижка по кошику, копійки
  },
  "items": [
    {
      "id": "…",
      "product_id": "РУ-043696",
      "price": 5000,
      "quantity": 2,
      "promocode_discount": 1500  // частка знижки на цю позицію, копійки
    }
  ]
}
```

Коли промокод не застосовано — `promocode: null`, `items[].promocode_discount: null` (або відсутнє поле — підтвердиться у Етапі 2).

`promocode_discount` per item — щоб фронт міг показати закреслену суму на рівні рядка. **Сума `items[].promocode_discount` == `promocode.total_discount`** (інваріант).

## 5. UX-flow

### 5.1 Apply

1. Користувач вводить код, натискає "Застосувати".
2. Фронт: дізейблити кнопку (idempotency на стороні бека — 60s, але це від double-click; не від навмисного re-apply).
3. POST `/apply-promocode`.
4. 200 → оновити cart-стейт з відповіді (повертається повний `cart`), показати знижку.
5. 422 → тост з повідомленням `error.message`. Для `PROMOCODE_USER_PHONE_MISSING` — додатковий CTA в профіль.
6. 503 → тост "сервіс недоступний, спробуйте за хвилину". Кнопку **не блокувати** — retry лежить на користувачі.

### 5.2 Implicit invalidation (КРИТИЧНО)

**Будь-яка зміна кошика (add / update quantity / delete) на стороні бека автоматично очищає `promocode_data`.** Це означає:

- Відповіді `POST /cart/items`, `PATCH /cart/items/{id}`, `DELETE /cart/items/{id}` можуть повернути `cart.promocode == null` навіть якщо до цього промокод був.
- Фронт повинен **завжди** оновлювати UI промокоду з останнього `cart`-респонсу, не тримати свій локальний стейт.
- Якщо промокод був і зник — показати тост: **"Кошик змінено, додайте промокод повторно"**.

Жодного окремого endpoint'а для "перевірити чи живий промокод" немає — стан промокоду завжди в `cart.promocode`.

### 5.3 Remove

DELETE `/remove-promocode` → оновити cart з відповіді. Окремої UX-обробки помилок не потрібно (операція ідемпотентна).

**Важливо:** якщо при apply-promocode було автоматично знято списання бонусів (див. §5.5), `remove-promocode` **не відновлює** його автоматично — користувач сам вмикає toggle бонусів якщо хоче.

### 5.5 Bonus vs promo — взаємовиключні (КРИТИЧНО)

За правилом 1С: **списання бонусів і знижка промокоду не можуть діяти на одному замовленні одночасно**. Тому:

- Якщо у користувача в кошику було вибране списання бонусів (`cart.bonuses_deducted > 0`) **до apply-promocode** — бек **автоматично** обнулить його після успішного apply (`cart.bonuses_deducted = 0`).
- Відповідь `POST /apply-promocode` повертає **повний `cart`** з оновленими полями. Фронт повинен:
  1. Перевірити інваріант: якщо `cart.promocode != null && cart.bonuses_deducted > 0` — це баг бекенда, треба сигналізувати в Sentry.
  2. Якщо до apply `bonuses_deducted > 0`, а після — `0`: показати додатковий тост: **«Списання бонусів скасовано: бонуси та промокод не діють одночасно»**.
- Якщо у користувача активний toggle "Списати бонуси" в UI — після apply-promocode фронт **тихо вимикає toggle** (оновлює UI-стейт з відповіді).
- При `remove-promocode` — бонусний toggle залишається вимкненим. Користувач сам вирішує чи вмикати його знову.

Earn (нарахування) cashback бонусів **не зачіпається** — він рахується на фінальну суму замовлення в обох випадках.

### 5.4 Checkout

Жодних додаткових дій для фронта. Бек сам:
- фіналізує знижку при створенні замовлення;
- може повернути `PROMOCODE_ALREADY_USED` / `PROMOCODE_EXPIRED` / `PROMOCODE_NO_ELIGIBLE_ITEMS` як 422 у відповіді на створення замовлення (race condition між пристроями).

Фронт показує `error.message`, повертає користувача на крок кошика, оновлює cart-стейт.

## 6. Edge cases для UI

- **Double-click apply.** Бек має idempotency (60s) — повертає той самий результат без повторного звернення до 1С. Фронт може полегшити — дізейбл кнопки до відповіді.
- **Race між пристроями.** Той самий код може бути застосований у двох кошиках, але закомітиться лише в одному замовленні. Інший пристрій отримає 422 `PROMOCODE_ALREADY_USED` на створенні замовлення — фронт мусить це обробити.
- **Час `period_to`.** Прийшов як ISO 8601 без TZ (`2026-04-11T00:00:00`). Інтерпретувати як локальний час сервера (Europe/Kyiv). Якщо UI показує countdown — це орієнтир, не блокування: фінальне рішення бере бек.
- **Зміна phone у профілі після apply.** Без особливої обробки. Якщо на checkout 1С відмовить — фронт побачить стандартний 422.
- **Bonus reset after apply** (див. §5.5). Якщо до apply було `bonuses_deducted > 0`, після apply воно стає 0. Single source of truth — response від `/apply-promocode`. Не намагатися «merge'нути» з локальним стейтом.
- **Re-apply того ж промокоду в межах 60s.** Бек повертає кешовану відповідь (idempotency). `bonuses_deducted` уже буде = 0, повторний toast про reset не показувати (порівнювати з `cart.bonuses_deducted` *до* кліку, не зі станом сервера).

---

## 7. Чого фронт **не** робить

- Не валідує формат коду крім "непорожній".
- Не зберігає список валідних промокодів локально.
- Не намагається перевірити промокод "тихо" у фоні — apply явний.
- Не парсить `error.message` — тільки `error.code`.
- Не намагається відновити промокод після зміни кошика автоматично — це рішення користувача.

## 8. Відкриті питання

- Точні значення enum `PromocodeErrorCode` (§3) — фіналізуються в Етапі 1 бекенда. До цього фронт може стабати на наведених `code`-стрингах.
- Чи буде окремий ендпоінт перевірки промокоду без застосування (preview) — **не передбачено в плані**, не очікувати.
- Дата викидання deprecated `/aply-promocode` — окремий PR після підтвердження міграції.
